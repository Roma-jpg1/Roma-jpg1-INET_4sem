# Вопросы для самопроверки

1. Какие критерии вы использовали при разделении монолита на микросервисы (или при проектировании сервисов)?

Разделял по бизнес-доменам и ответственности: пользователи (`user-service`), посты (`post-service`), лайки (`like-service`). Каждый сервис владеет своей БД, чтобы снизить связность и упростить независимые изменения и деплой.

2. Почему вы выбрали именно этот стек технологий (язык, БД, протоколы)?

Выбран Python + FastAPI как быстрый и понятный стек для учебного микросервисного проекта. PostgreSQL использован как надежная реляционная БД. REST применен для внешнего API, а gRPC для межсервисного вызова `post-service -> like-service`, где важны четкий контракт и скорость.

3. Как ваши сервисы справляются с ошибками (retry, circuit breaker, graceful degradation)?

В `post-service` gRPC-вызов к `like-service` обернут в `try/except`: если лайки недоступны, сервис не падает и возвращает пост с `likes_count = 0` (graceful degradation). Это сохраняет работоспособность внешнего API при частичных сбоях.

4. Как организован деплой и обновление вашей системы без простоя (Zero Downtime)?

Локально деплой идет через Docker Compose (`up --build`). Для прод-сценария без простоя подходит rolling update в Kubernetes/оркестраторе: запуск новой версии, проверка healthcheck/readiness, переключение трафика и только потом остановка старых экземпляров. В текущем учебном проекте это описано на уровне архитектурного подхода.

5. Что было самым сложным в интеграции всех компонентов вместе?

Самым сложным было синхронизировать запуск HTTP и gRPC в `like-service`: gRPC-сервер не стартовал, пока `lifespan` не был корректно подключен к FastAPI. После исправления и проверки портов (`50051`) связка заработала.

6. Что бы вы улучшили, если бы у вас был еще месяц?

Добавил бы полноценную наблюдаемость (Prometheus + Grafana + structured logs), retry/backoff и circuit breaker для межсервисных вызовов, миграции БД (Alembic), API Gateway и расширил CI/CD до автодеплоя в staging.
