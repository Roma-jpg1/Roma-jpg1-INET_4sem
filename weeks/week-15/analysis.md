# Анализ производительности (`profiles-s18`)

На этой неделе я проверил как ведет себя сервис при росте нагрузки
Смотрел две вещи сколько запросов в секунду он выдерживает throughput RPS и как меняется latency

Проверял `GET /api/profiles` и `POST /api/profiles` на трех уровнях параллельности `1` `10` и `100`

## Данные по GET `/api/profiles`
- При concurrency `1` примерно `2198.53 RPS` средняя latency `0.46 ms` `P95 = 0 ms` `P99 = 1 ms`
- При concurrency `10` примерно `4625.13 RPS` средняя latency `2.16 ms` `P95 = 2 ms` `P99 = 3 ms`
- При concurrency `100` примерно `5567.67 RPS` средняя latency `17.96 ms` `P95 = 20 ms` `P99 = 33 ms`

## Данные по POST `/api/profiles`
- При concurrency `1` примерно `2075.64 RPS` средняя latency `0.48 ms` `P95 = 0 ms` `P99 = 1 ms`
- При concurrency `10` примерно `4297.01 RPS` средняя latency `2.33 ms` `P95 = 3 ms` `P99 = 4 ms`
- При concurrency `100` примерно `4892.62 RPS` средняя latency `20.44 ms` `P95 = 23 ms` `P99 = 39 ms`

## Что это значит простыми словами
- Когда увеличиваем нагрузку с `1` до `10` сервис ускоряется хорошо RPS растет сильно задержки остаются комфортными
- Когда идем дальше с `10` до `100` прирост по RPS уже не такой большой зато latency растет очень заметно
- Это признак приближения к насыщению система еще работает но цена в задержках становится высокой

## Итог
Для моего варианта самый адекватный режим из этих трех около concurrency `10` скорость хорошая и latency еще не плывет
